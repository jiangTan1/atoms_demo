# 项目文档：网页应用生成智能体（demo）

本文档面向开发者与后续维护者，说明这个 demo 的**实现思路与关键取舍**、**当前完成程度**，以及**继续投入时的扩展方向与优先级判断**。

- 使用方式、配置项、接口清单与部署步骤见 [README.md](../README.md)。
- 历次变更的需求与设计依据见 [openspec/changes/](../openspec/changes/) 下的 `proposal.md` / `design.md` / `specs/`。

---

## 1. 项目定位

一个**对话式网页应用生成器**：用自然语言描述想要的网页应用（如「做一个俄罗斯方块小游戏」），智能体把构成应用的 HTML / CSS / JS 文件真实写入**按会话隔离的服务端沙箱**，并在对话界面**右侧即时预览**、可直接操作。生成之后可以继续用对话改功能、加需求；每轮有效改动会**自动留档为一个版本**、随时回滚（回滚可逆）；也可以为某个版本生成**公开只读分享链接**，发给任何人免登录打开。

访问服务需先**注册或登录**：未登录只能停在认证界面，登录后各人的会话、沙箱与版本互相隔离，归属由登录态决定、客户端无法指定或伪造。生成的网页应用通过客户端沙箱（限制能力的 iframe）运行，服务端不执行应用代码。

技术栈：Python 3.12 + Google ADK 2.10.0 + LiteLLM + FastAPI + 原生 HTML/JS（无前端构建）。

## 2. 架构与数据流转

分层结构（自上而下）：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 配置层 | [config.py](../app/config.py) | 读 `.env`，校验必填项与取值（含沙箱三项配额、版本上限与单轮生成时限），缺失/非法时启动失败并点名配置项 |
| 模型接入层 | [model.py](../app/agent/model.py) | 用 ADK `LiteLlm` 包装任意 OpenAI 兼容端点，端点/模型/凭据全部来自配置 |
| Agent 层 | [root_agent.py](../app/agent/root_agent.py)、[prompt.py](../app/agent/prompt.py)、[tools.py](../app/agent/tools.py) | `LlmAgent` 单例：静态 instruction（`prompts/system.md`，含「先出骨架、再增量填充」与「应用完整外壳」两节）+ 四个沙箱文件工具 |
| 服务层 | [runner.py](../app/services/runner.py)、[chat.py](../app/services/chat.py)、[workspace.py](../app/services/workspace.py)、[examples.py](../app/services/examples.py)、[versions.py](../app/services/versions.py)、[shares.py](../app/services/shares.py)、[accounts.py](../app/services/accounts.py) | Runner 与会话后端生命周期、Event→SSE 帧归一化（含单轮时限与失败归类）、会话沙箱（入口定位/从模板初始化/快照/打包）、内置示例清单与模板复制、版本留档与回滚、分享记录与 token 解析、账号库与登录态令牌 |
| 接口层 | [api/auth.py](../app/api/auth.py)、[api/chat.py](../app/api/chat.py)、[api/sessions.py](../app/api/sessions.py)、[api/workspace.py](../app/api/workspace.py)、[api/versions.py](../app/api/versions.py)、[api/preview.py](../app/api/preview.py)、[api/shares.py](../app/api/shares.py)、[api/examples.py](../app/api/examples.py) | 鉴权依赖与认证/管理员接口、SSE 对话（超时/中断不留档）、会话管理、打包下载、版本列表与回滚、会话内应用预览、分享管理与免登录分享预览、内置示例列表与选用 |

**一次对话的数据流转**：

```
浏览器 --POST /api/chat (JSON + 登录态 Cookie)--> 接口层
  接口层：鉴权依赖校验 Cookie 令牌 → 取到登录用户名 → 归属记为 user:<用户名>
  接口层：解析/创建会话 → 推导澄清轮次 → 拼装用户消息前缀
  服务层：asyncio.timeout(CHAT_TIMEOUT_SECONDS) 包住整轮，例外转可重试的 error 帧
  服务层：runner.run_async(StreamingMode.SSE) 驱动 Agent
     Agent：模型（LiteLLM）→ 可能发起 function call → 四个文件工具 → 沙箱读写
  服务层：ADK Event 归一化为帧（增量文本 / 完整文本 / error / done）
  接口层：包装为 text/event-stream（data: {json}）
  接口层收尾：本轮无 error 帧时比对沙箱指纹，有变化则留一个版本快照（失败不影响已完成的对话流）
浏览器：逐帧渲染（打字机 + 「正在生成第 N 行 · 已用 M 秒」进度）→ 结束后用完整帧兜底 → 渲染 Markdown/高亮/代码块按钮
浏览器：失败（超时 / 限流 / 网络 / 中断）→ 失败提示 + 「重试」原样重发；生成中可点「中断」断开本轮
浏览器：顶栏「示例应用」--GET /api/examples--> 列表；--POST /api/examples/apply--> 新会话 + 模板写入沙箱（免生成即预览）
浏览器：预览区 --GET /api/sessions/{会话}/preview-token--> 校验归属后签发票据
浏览器：刷新预览区 --GET /preview/{会话}/{票据}/--> 沙箱入口页（iframe 不透明源隔离）
```

**三条并行的落盘链路**：会话（`data/sessions.db`，ADK 持有 schema）、版本快照（`data/versions/<会话>/<版本>/`，整目录副本）、分享记录（`data/shares.db`，自建表）。三者互不依赖，任一后端切换或损坏都不会连带影响另两条。

**三层归一化**是这套设计的骨架：`ADK Token/Event → 服务层 Frame → 接口层 SSE 文本`。每一层只关心自己的契约，因此换模型、换前端、换部署方式都不会互相牵连。

## 3. 实现思路与关键取舍

### 3.1 模型与提示词：能力靠配置，约束靠提示词 + 服务端兜底

- **模型零硬编码**：`LLM_MODEL` / `LLM_BASE_URL` / `LLM_API_KEY` 全走环境变量，切换模型只改 `.env`（demo 默认智谱免费的 `glm-4.5-flash`）。
- **静态 instruction 是刻意的**：`LlmAgent` 是模块级单例，instruction 进程内不变。因此**澄清轮次**这类每轮都变的信息不走 instruction，而是以用户消息前缀 `[澄清轮次：n/5]` 注入（[chat.py](../app/services/chat.py) 的 `compose_user_message()`），还原历史时再统一剥离，避免内部标记泄漏到页面。目标语言的同类前缀机制保留在服务端，但定位收窄为「网页应用生成」之后界面已不再暴露该选项。
- **取舍**：放弃「按会话动态重建 Agent/工具集」的灵活性，换取单例的简单与低开销；代价是每轮要变的东西只能走消息前缀。

### 3.2 流式：增量打字机 + 流结束后的一次完整帧

- 增量帧负责打字机体验，`partial=false` 的完整帧负责「增量丢帧时兜底」。
- **挂上文件工具后必须改**：一轮对话会出现「文本 → 工具调用 → 更多文本」的交替，`partial=false` 不再等价于「本轮最终回复」，而 `is_final_response()` 按本版本实现会把中间的纯文本聚合事件误判为最终回复。
- **做法**：把完整帧的产出**从事件分支移出**，改在事件循环结束后用累积文本产出一次。
- **为什么这样取舍**：判定依据从「某个事件标记」变成「流已结束」，不依赖 ADK 对 `partial` / `is_final_response` / 未来 `turn_complete` 的语义约定，契约更稳。代价是完整帧晚一次循环收尾的时间到达，使用者不可感知。
- 另一个坑：SSE 模式会同时下发**增量片段**和**本轮聚合事件**，聚合文本整体再累积一次就会重复。因此用「最长重合」算法（`_unseen_suffix()`）只保留真正新增的尾段，同时兼容「聚合比增量更完整」的情形。

### 3.3 会话：惰性创建 + 落盘 + 轮次推导

- **惰性创建**：新建会话不预先落库，首次提问时才创建，避免历史列表堆出空会话。
- **可切换后端**：`SESSION_BACKEND=sqlite`（默认，落盘 `data/sessions.db`，刷新/重启后仍有历史）或 `memory`（仅进程内）。
- **澄清轮次由服务端推导**，不信任模型自报：从最新事件向前数**连续**的「带 `[[CLARIFY]]` 标记的助手回复」，遇到第一个无标记的实质回答即停止（[chat.py](../app/services/chat.py) 的 `count_clarify_rounds()`）。达到 5 次上限时**不再请求模型**，直接返回固定结束语并补写进会话。
- **取舍**：轮次计数依赖模型按约定在回复首个内容位输出标记。这是提示词层面的软约束，属于已知限制（见 §4.3）。

### 3.4 意图边界：提示词约束，而不是关键词过滤

三类边界全部写在 [prompts/system.md](../prompts/system.md) 的「意图识别与边界」章节：

1. **范围外**（与网页应用无关，如闲聊、生活咨询、其他专业领域）→ 固定回复「我是一个网页应用生成智能体，只能根据需求生成和修改网页应用……」，不顺着话题展开；边界模糊但仍可理解为「想做个网页应用」的输入按需求处理或先澄清，不直接拒答；
2. **法规与安全风险**（如探测/攻击公开网络服务或政府网站）→ 拒答且不写入沙箱；
3. **意图不明确**（缺实现必需的关键信息，如玩法规则未定）→ 先澄清（一次最多 3 个问题或给选项），最多 5 轮。

**取舍**：不用关键词黑名单，而交给模型判断。好处是能理解语义、能区分「范围外」与「可合理理解为网页应用需求」（例如「我想做个能算账的东西」）；代价是边界个例可能超出预期，且换模型会带来行为漂移。

### 3.5 文件沙箱：会话隔离、可证明的边界、有上界

目录固定为 `data/workspace/<会话标识>/`（与 `sessions.db` 同层，`data/` 已被忽略）。

关键取舍逐条：

| 取舍点 | 选择 | 放弃的方案与理由 |
| --- | --- | --- |
| 沙箱粒度 | 一会话一目录 | 共享工作区（同名文件互相覆盖，「一个会话一个项目」语义消失） |
| 工具来源 | **自写四个函数工具** | ADK 自带 `tools/environment` 工具族（沙箱根在 `environment` **构造时**固定，无法随会话变化；缺列目录/删除，却带了一个明确不要的 `ExecuteTool`） |
| 会话标识传递 | 经 `tool_context` 注入（`tool_context.session.id`） | 闭包绑定 / 写 `session.state`（都要在构建期或写路径上做额外改造，收益不足） |
| 路径安全 | **显式拒绝绝对路径与 `..` → 再 `resolve()` 后校验真实路径仍在沙箱内** | 字符串前缀匹配（符号链接与 `..` 可绕过）；正则过滤危险字符（Windows/POSIX 语义不同，必然漏） |
| 占用上界 | 三个可选配置项：单文件 256 KB / 文件数 200 / 总量 10 MB，超限在落盘前拒绝 | 硬编码（上线后调整要改代码）；交给模型自己控制（配额是服务端强制约束，不能依赖模型判断） |
| 工具失败 | **以文本结果回灌给模型**，不产生 `error` 帧、不中断对话 | 升级为 SSE 错误帧（会把可自愈的参数错误变成使用者可见的连接错误） |
| 打包 | 标准库 `zipfile` 内存打包 | 引入流式打包库（配额已把规模压到 10 MB 级，收益不存在）；逐文件下载（与「一键取走整套」目标不符） |
| 下载入口 | 顶栏按钮 + `fetch` + 复用既有 `saveAsFile()` | `<a href>` 直链（空沙箱时会下载到错误内容，无法给提示）；放在每条回复下方（同一会话会有多个入口，语义混乱） |
| 预览取件方式 | **把沙箱目录当静态站点根**，按相对路径直出文件（入口固定 `index.html`，资源用相对路径） | 单文件端点逐个列举（多文件应用要逐个登记）；构建/打包后预览（违背「无需构建即可运行」的产物约定） |
| 版本快照形态 | `shutil.copytree` 整目录副本到 `data/versions/<会话>/<版本>/` | 用 git 管理版本（引入外部依赖与仓库状态，且沙箱并非代码仓库）；增量 diff（回滚要重放，复杂度陡增） |
| 「是否有改动」判定 | 文件清单 + 各文件 `sha256` 组成指纹，存 `<会话目录>/.state.json`，与上一轮指纹比对 | 按轮次无脑留档（纯问答也产版本，列表被噪音淹没）；写 `session.state`（会与 ADK 会话 schema 耦合） |
| 分享指向 | **版本快照**，而不是当前沙箱 | 指向当前沙箱（后续对话会悄悄改掉已发出的分享内容）；打开时现算（无法保证内容稳定） |
| 回滚方向 | 回滚前**先把当前内容留存为新版本**，再整体替换 | 直接覆盖（回滚不可逆，改坏了再也回不去）；移动/重命名目录（列表顺序混乱，且会丢历史） |

两个容易忽略的「白拿」结论：

- `function_call` / `function_response` 部件没有 `.text`，会被文本提取天然跳过 → **工具调用不会在历史里留下多余消息**，也不干扰澄清轮次计数。
- 沙箱里写文件**不代表**写了正确的应用：本版仍不做内容校验（见 §4.2）——但预览把「写得好不好」立刻暴露给使用者，比「只下载到本地才知道」的反馈环路短得多。

### 3.6 前端：左对话右预览、零构建、可降级

- 原生 HTML/JS，无打包工具；通过 cdnjs 引入 `marked` / `highlight.js` / `DOMPurify`。
- **布局**：`.workspace` 是「左侧对话 + 右侧应用预览」的横向两栏（46% / 54%），窄屏（≤640px）改为上下排布，避免左右并排被挤压溢出。
- **预览面板**：`iframe` + 「刷新」按钮 + 状态提示。刷新时**先探一次入口页状态码**，据此分流：401 → 交给 401 集中处理；404 → 展示服务端给的中文 `detail`（区分「空沙箱」与「有文件但无入口」）并置状态为「尚无应用」；其它非 2xx → 「加载失败（HTTP xxx）」；2xx → 把 `iframe.src` 指向入口页（带时间戳参数强制重载）。
- **版本与分享弹层**：复用既有 `.modal` 形态。版本弹层倒序展示版本、确认后回滚（回滚成功重取预览与列表）；分享弹层选版本生成链接（成功后自动复制）、列出自己已创建的分享、可复制与撤销。
- **降级策略**：任一 CDN 不可达时，页面自动退化为纯文本展示，对话与复制仍可用，**不白屏**。
- 代码块上「复制」与「另存为」并排；另存为按语言决定扩展名，同轮同名自动加序号。
- 安全：Markdown 渲染结果统一经 `DOMPurify` 清洗后再注入；预览 `iframe` 与主站之间靠 `sandbox`（不给 `allow-same-origin`）隔离，详见 §4.3「已知限制」。
- **设计令牌与暗色**：`styles.css` 顶部用一组 CSS 变量统一间距（8px 基准）、圆角、字号层级、配色与阴影；暗色令牌写两份（`html[data-theme="dark"]` 与 `@media (prefers-color-scheme: dark)`）以同时支持手动切换与跟随系统。预览画布固定白底，不随界面主题变暗（生成的应用是浅色自包含页面）。

### 3.7 部署取向：单机、反代、可开机自启

单机部署：**Nginx 反向代理 + systemd 托管 uvicorn**，应用只监听 `127.0.0.1:80`，不直接对外。端口默认值即 `80`，因此**后端占用了 80**——Nginx 样例只保留 `443` 并反代到 `127.0.0.1:80`，不监听 80（若要把 80 留给 Nginx 做跳转或 ACME webroot，需同时改 `APP_PORT`）。Linux 下绑定 80 属特权端口，systemd 单元里用 `AmbientCapabilities=CAP_NET_BIND_SERVICE` 授权，不整机以 root 跑服务。两处与流式强相关的配置：`proxy_buffering off`（否则没有打字机效果）与 `proxy_read_timeout 300s`（默认 60s 会切断长代码回复）。样例另含按来源 IP 的限流。详见 [README.md](../README.md) 的部署章节。

### 3.8 认证与账号：登录态贯穿，归属只认登录身份

改造前 `user_id` 是**客户端自报**的请求字段（默认 `web-user`），服务端无条件信任。本次把这层信任收回服务端，落到四个取舍点上：

| 取舍点 | 选择 | 放弃的方案与理由 |
| --- | --- | --- |
| 账号存储 | 独立的 `data/users.db`（标准库 `sqlite3`） | 塞进 `data/sessions.db`（schema 由 ADK 持有，且 `SESSION_BACKEND=memory` 时会话不落盘、账号会随之丢失）；引入 ORM（关系足够简单，不值得加依赖） |
| 登录态 | 服务端随机令牌 + HttpOnly Cookie（`SameSite=Lax`、1 天有效） | JWT / 签名 Cookie（改密后「使其他登录态失效」要额外维护吊销名单）；令牌放 `localStorage`（脚本可读，XSS 面更大） |
| 鉴权落点 | 各路由声明 FastAPI 依赖 `Depends(current_user)` | 全局中间件按路径白名单放行（白名单与路由定义分离，新增接口容易漏配） |
| 会话归属 | 统一用 `user:<登录用户名>` 作 ADK 的 `user_id` | 直接用用户名（`web-user` 是合法用户名，任何注册到该名字的人会看到历史匿名会话）；不做迁移（破坏性操作） |

几张具体的账：

- **密码哈希**用标准库 `hashlib.pbkdf2_hmac("sha256", …, 260000, salt=16B)`，存储格式自带参数 `pbkdf2_sha256$<迭代>$<盐>$<哈希>`，校验用 `hmac.compare_digest()` 定时安全比对；「用户名不存在」与「密码错误」返回同一类失败，并都做一次同样开销的哈希，避免用响应差异探测账号是否存在。
- **99 上限的口径落到数据上**：账号表加 `source` 列（`system` / `self` / `admin`），上限判定为 `role='user' AND source='self'` 的行数 < 99，因此内置管理员（`system`）与管理员新增（`admin`）都不占名额。
- **改密入口的取舍**（design 决策 11）：改密在语义上要求「证明你是这个账号」，而认证界面是未登录态。若在认证界面串联「登录 → 改密 → 退出」，会留下短暂的中间登录态、且失败路径状态不清。最终把改密收进**对话界面顶栏的弹层**（原密码 + 新密码，用户名取当前登录用户），一次请求、无中间态；认证界面上的「修改密码」按钮只作入口提示。
- **前端 401 集中处理**：对话、会话列表、历史消息、打包下载四处请求任一返回 401 即切回认证界面并提示重新登录，四种失败态都不出现白屏。

### 3.9 生成过程的可控性：单轮时限、中断、示例应用与界面主题

「生成要等多久、能不能取消、失败怎么办」原本是黑盒，本节把这几处补上（见变更 `improve-generation-ux`）。

| 取舍点 | 选择 | 理由与放弃的方案 |
| --- | --- | --- |
| 时限窗口 | **单轮 240s**，`asyncio.timeout` 从发起到本轮 SSE 结束（不跨模型调用累计） | 与「一轮对话 = 一次可重试的操作」语义对齐，前端只需一个中断按钮。逐次模型调用分别设超时，会让多轮工具调用的总耗时仍不可控；240s 仍小于部署样例的 `proxy_read_timeout 300s`，由应用先中止，代理不会抢先断开 |
| 超时表现 | 回一帧 `error`（`upstream_error` + 中文说明）再回 `done`，**不产出** `partial=false` 完整帧 | 不新增第四类错误码（既有三类已够用，超时/限流靠消息说清事实）；「内容不完整 ⇒ 没有完整帧」让前端天然不会把半截内容当成品，也便于接口层据此跳过版本留档 |
| 主动中断 | 前端 `AbortController` 断开请求 → 服务端协程被取消（`CancelledError` 透传，不回帧） | 连接已断，回帧无人接收；沙箱里已写入的文件保留，不做回滚（与「生成失败不留版本」一致） |
| 执行中反馈 | 状态区每 500ms 刷新「正在生成第 N 行 · 已用 M 秒」，未收到文本时显示「正在等待模型响应」 | 行数从已接收文本推导，比伪造百分比更诚实（模型不返回 token 进度）；`done` 帧也不能加字段（会破坏既有帧协议断言） |
| 失败归类 | 仅 `error` 帧出现即视为本轮失败：接口层跳过留档；前端给出「重试」按钮原样重发 | 客户端中断时生成器被取消、收尾逻辑自然不执行，无需额外标记 |
| 示例应用 | 模板放版本库 `templates/examples/<id>/`，选用时**复制进新建会话的沙箱** | 复制后即可复用既有预览/版本/分享/下载/继续对话全链路，完全不走模型；放弃「前端静态展示示例」——那样就不能改、不能分享 |
| 示例与惰性创建 | 选用示例是「新建会话惰性创建」的**唯一例外**，立即建会话并写沙箱；失败则回退（删会话 + 清沙箱） | 只有先落库并写好沙箱，「点开即预览」才成立；回退保证不出现「有会话但沙箱残缺」 |
| 复杂需求 | 提示词要求「先出骨架、再增量填充」：先写 `index.html` 骨架，再逐个补 `style.css` / `app.js`，内容多则分批 | 避免一次性把整套应用塞给模型撞上单次生成长度上限，也让「生成中」的推进可见 |
| 界面设计系统 | **零构建 + 自建设计令牌**（CSS 变量 + `prefers-color-scheme` / `html[data-theme]` 双层暗色） | 明确不引入 Tailwind / antd 与构建链，保持「原生 HTML/JS、无打包工具」的既有约束；令牌统一间距、圆角、字号层级、配色与阴影，只作用于**助手自身界面**，不强加给生成的应用 |
| 代码高亮暗色 | 同时引入 `github` 与 `github-dark` 两份样式表，随主题切 `link.disabled` | 切换不重新下载，也不需改动 `highlight.js` 的调用方式 |

### 4.2 明确不做（有意为之的能力边界）

- **不给智能体执行命令、安装依赖、访问网络的能力**——只做沙箱内的文件读写与列目录/删除。
- **不做文件内容校验**：不判断模型写的代码是否正确、是否可运行；写了不代表对。
- **不做细粒度资源 ACL**：本版只区分「管理员」与「普通用户」两种角色，不做「按资源授权 / 共享协作 / 团队空间」。
- **不做登录防护策略**：不做登录失败锁定、验证码、口令复杂度与找回密码（含邮件/短信）；3 字符下限是有意为之，便于演示。
- **不做多设备与登录态管理**：不做「记住我」、设备列表、登录态续期与刷新令牌；每账号最多保留 1 天有效的令牌，改密只吊销其他登录态。
- **不做既有匿名会话的迁移与认领**：升级后旧会话（`user_id=web-user`）不再对任何用户可见，数据仍保留在 `data/` 中，但系统不提供迁移或认领入口。
- **不做沙箱清理与生命周期回收**：历史会话当前不支持删除；版本快照也随会话累积（受单会话版本上限约束）。
- **不做文件清单界面与单文件下载**：沙箱只提供「整包下载」、应用预览与版本回滚，不逐个列出文件、不支持单文件下载。
- **不在服务端运行生成的应用**：应用只在浏览器（预览/分享的 iframe）里跑，服务端不执行任何模型产出的代码。
- **不做协作与在线编辑**：分享是**只读**的，访问者不能对话、不能改应用；不引入多人协作或版本评论。

### 4.3 已记录的已知限制

- 沙箱不随会话「新建」而清理，`data/workspace/` 会随使用累积，需手动删除；同一会话并发写同一路径**以后写者为准**（无文件锁）。
- **单轮生成有 240 秒硬上限**（`CHAT_TIMEOUT_SECONDS`）：超时由服务端主动中止并给出可重试的失败提示，该轮不留版本，但已写入沙箱的文件仍在。需求过大时需拆成多轮分批补。
- **示例模板需与代码一起发布**：`templates/examples/` 不属于 `data/`，是版本库的一部分；部署时若只同步 `app/` 与 `web/` 会缺少模板，`GET /api/examples` 会返回「示例清单不可用」。
- **版本快照会额外占用磁盘**：每轮有效改动都整目录复制一份到 `data/versions/<会话>/<版本>/`，单会话最多保留 `VERSION_MAX_PER_SESSION`（默认 20）份、超出后清理最旧；`data/versions/` 与 `data/workspace/` 同样只增不减，需手动清理。
- **既有无入口文件的会话在预览区只给提示**：改造前创建的会话沙箱里没有 `index.html`，预览会提示「缺少入口文件」而不是报错，需通过对话让智能体补齐入口页，或直接整包下载。
- **分享是免登录读入口**：任何人拿到链接即可只读访问，不校验身份、不记录访问者；已按来源 IP 在 Nginx 限流以缓解 token 枚举与流量滥用，但链接一旦外泄即等同于内容公开，撤销是唯一的止损手段。
- **BREAKING**：升级后既有匿名会话（`user_id=web-user`）不再对任何用户可见，数据保留在 `data/` 未迁移。
- **无 HTTPS 时口令与登录态 Cookie 明文传输**：部署需由 Nginx 终止 TLS，并在 HTTPS 就绪后把 `AUTH_COOKIE_SECURE` 置为 `true`；HTTP 仅限本机与内网演示。
- **首个管理员只由配置项创建，没有固定的默认口令**：首次启动且 `data/users.db` 为空时必须提供 `ADMIN_USERNAME` / `ADMIN_PASSWORD`（缺失即启动失败并点名该项），创建后不再读取这两项，因此不会用配置值覆盖后来改过的密码；但用户名与密码的 3 字符下限仍偏松，属演示级取舍，上线务必使用强口令。
- **端口 80 属特权端口**：本机监听 80 需要相应权限（Windows 通常需管理员身份运行；Linux 由 systemd 的 `CAP_NET_BIND_SERVICE` 授权）。若换回 8000 等高位端口，只需改 `.env` 的 `APP_PORT` 并同步 systemd 单元与 Nginx 的 `proxy_pass`。
- **管理员操作只有接口、没有界面**：新增 / 重置 / 删除用户以接口形式提供，使用门槛较高（README 给了可直接复制的调用示例）。
- **登录态有效期固定 1 天**：到期即失效需重新登录，不做续期或「记住我」。
- **用户名区分大小写**：`Alice` 与 `alice` 可并存，可能出现混淆；本版按原样保存与比较，未做规范化。
- 生成项目依赖模型稳定触发 `function call`；免费模型 `glm-4.5-flash` 实测可用，但**能力较弱的模型可能仍只输出文本、不落盘**（此时仍可用代码块的「另存为」单个取出）。
- `glm-4.5-flash` 偶发以英文作答、或在开头复述任务。
- 澄清追问依赖模型在回复首个内容位输出 `[[CLARIFY]]`：未输出则该轮不计次、上限不推进；**若标记出现在非首位**（例如模型先复述一行任务再提问），则标记会显示在页面上且该轮不被计为追问——这是模型侧偏差，非服务端逻辑问题。
- 领域外与法规风险边界由提示词约束，属模型判断而非关键词过滤，个例可能超出预期。
- 前端依赖 cdnjs；离线需自行 vendor 三个库（注意 jsdelivr 在部分网络下不可达）。
- **顶层直达预览/分享的应用地址会绕过 iframe 沙箱**：`/preview/<会话>/<票据>/` 与 `/share/<token>/app/` 被 iframe 嵌入时处在不透明源（脚本读不到 `document.cookie` 与 `localStorage`，已实测），但直接在地址栏打开时文档落在主站源上，只剩 CSP 的 `connect-src 'none'` 在挡「联网」。根因是预览仍挂在主站同源路由上，彻底解决要迁到独立源（见 §5 第 11 项）。
- **预览票据放在路径里，而不是靠登录态 Cookie**：不透明源 iframe 自己发出的子资源请求被浏览器视为跨站，`SameSite=Lax` 的登录 Cookie 不跟随，会得到 401 并被 Chrome 的 ORB（`net::ERR_BLOCKED_BY_ORB`）拦掉，使预览里样式与脚本全部失效（表现为「界面看得见、点不动」）。故预览入口为 `/preview/<会话>/<票据>/`：相对路径自动继承同前缀票据，子资源无需 Cookie。票据由 `app/services/preview_token.py` 以 HMAC 签发，绑定会话、默认 1 小时有效，只能由已登录且会话归属本人的使用者通过 `GET /api/sessions/{session_id}/preview-token` 换取。
- 未标注语言的代码块只做等宽展示，不做高亮猜测。
- 达到追问上限那一轮的回复由服务端直出并补写会话；补写失败则该轮不入库（刷新后看不到最后一轮，但刚收到的回复内容不受影响）。
- LiteLLM 会尝试联网拉价格表，网络受限时已在启动脚本与 systemd 单元中改用内置表。

### 4.4 工程状态上的「未完成」

- **OpenSpec 变更尚未归档**：`openspec/changes/` 下现有 6 个变更（`add-code-assistant-agent`、`add-session-history-and-bug-finding`、`add-scope-guardrails-and-output-rules`、`add-workspace-file-tools`、`add-user-authentication`、`add-web-app-builder`）都是活动变更，`openspec/specs/` 仍为空。规范沉淀在 `changes/` 里，未同步为「当前系统规范」。按 OpenSpec 流程，功能验证通过后应 `sync` 并 `archive`。

## 5. 后续扩展与优先级判断

优先级依据三条标准：**（a）不解决会产生正确性、安全或成本上的实质风险；（b）是否解锁后续能力；（c）性价比（改动量 vs 收益）**。

### P0 — 上线前必须解决（不解决就有实质风险）

1. **访问控制（基础版已完成，剩「登录防护」补强）** —— ✅ 已由 `add-user-authentication` 变更落地
   - 已完成：全站登录门控（未登录不得进入对话界面，也不得触发任何业务动作）、会话与沙箱按登录用户隔离、下载接口按归属校验、密码加盐哈希与定时安全比对、自助注册 3–20 字符与 99 上限、首个管理员由 `ADMIN_USERNAME`/`ADMIN_PASSWORD` 在首次启动时创建（无默认口令）、管理员增删改用户。
   - 剩余（可选补强）：不做登录失败锁定、验证码、口令复杂度与找回密码（见 §4.2），暴力猜解目前仅靠 Nginx 的按来源 IP 限流缓解；如需对外长期运行，建议补一层登录失败计数与短时锁定。
   - 前置依赖：无。

2. **沙箱与版本的清理与生命周期**
   - 现状：`data/workspace/` 与 `data/versions/` 都只增不减，长跑会吃满磁盘（沙箱虽有单会话 10 MB 上限、版本有单会话份数上限，但会话数无上限）。
   - 理由：运维风险，且会连带影响 P1 的「历史会话删除」。
   - 做法：先加「删除会话」接口（连同该会话的沙箱目录与版本快照一并删），再加一个按时间/容量回收的清理任务。
   - 前置依赖：会话删除能力。

3. **锁定单实例部署约束（或改造为多实例可用）**
   - 现状：会话落 SQLite，`--workers 1` 才能避免并发写冲突。
   - 理由：这是横向扩展的硬约束，需要**明确选择**：要么在文档与部署样例里把它固化为前提，要么把会话后端抽象成可替换实现（Postgres/Redis）。
   - 建议：现阶段固化约束、补一条健康检查与自动重启即可；真要多实例再动后端。

### P1 — 能力补齐（决定「像不像真的能干活」）

4. **生成应用的静态校验（沙箱内只读校验优先）**
   - 现状：写入的 HTML/CSS/JS 不做任何语法或结构校验——预览已经把「能不能跑」立刻暴露出来，但报错只堆在浏览器控制台，智能体自己也看不到。
   - 理由：把「预览发现坏了 → 用户描述问题 → 再改一轮」的往返，缩短为「服务端先自查、把明显错误带进下一轮上下文」。
   - 风险与取舍：**执行任意模型生成的代码风险很高**，本版连服务端执行都不做。建议只做**静态校验**（JS 用 parser 做语法检查、HTML 结构检查、引用资源是否存在），不改「服务端不执行应用代码」这条底线。
   - 前置依赖：无（真要做受限执行再依赖 P0-1 的登录门控）。

5. **沙箱文件清单与单文件下载**
   - 现状：预览只呈现「运行结果」，沙箱里的文件清单对使用者仍不可见，想拿到源码只能整包下载。
   - 理由：改动小、体验提升明显；也能部分缓解「模型声称写了但没写」的不信任。
   - 做法：复用 `list_files()` 加一个 `GET /api/workspace/files`，前端加一个列出文件与单文件下载的侧栏。

6. **模型能力兜底与降级路径**
   - 现状：能力弱的模型不触发 `function call` 时，功能形同虚设且使用者不知情。
   - 做法：检测「用户要求生成项目但本轮无任何文件写入」，在回复后追加一条明确提示（并给出代码块另存为的替代路径）；长期可换更稳的模型或加「强制落盘」开关。
   - 理由：把不可控的模型差异变成使用者可理解的提示，性价比高。

### P2 — 体验与规模化（锦上添花）

7. **会话管理完善**：重命名、删除、搜索（当前只支持浏览与切换）。
8. **停止生成 / 请求取消**：长回复目前只能等它跑完。
9. **长对话与长代码的渲染性能**：折叠代码块、虚拟滚动、增量渲染节流。
10. **可观测性与成本**：按会话统计 token 与请求量、结构化日志、错误率告警。
11. **预览与分享迁到独立源（子域或独立端口）**：本版预览/分享仍挂在主站同源路由上，iframe 嵌入时靠 `sandbox`（不给 `allow-same-origin`）隔离成不透明源，但**直接在地址栏打开应用地址会绕过 iframe、落在主站源上**（见 §4.3）。把预览迁到独立源后，顶层直达也不再与主站同源，这是消除该残余风险的正解；代价是部署要多一个域名/端口与证书。
12. **离线可用**：把三个 CDN 库 vendor 到 `web/vendor/`。
13. **OpenSpec 归档**：把已验证的 6 个变更 `sync` 进 `openspec/specs/` 并归档，让规范从「变更记录」变成「当前系统规范」。

### 建议的推进顺序

```
第一步（上线加固）：P0-2 会话/沙箱/版本删除 → P0-3 单实例约束固化（P0-1 访问控制基础版已完成，可按需补登录失败锁定）
第二步（安全收口）：P2-11 预览/分享迁独立源 → P1-4 应用静态校验 → P1-6 模型降级提示
第三步（能力补齐）：P1-5 文件清单与单文件下载 → P2 各项按需
```

**判断依据一句话**：P0 里访问控制这一安全缺口的基础版已落地（登录门控 + 归属隔离），剩下的 P0-2、P0-3 是「不做会在磁盘或扩展性上出事」的硬缺口，且都**改动小**；P2-11 是当前唯一已知的、可被利用的隔离残余（顶层直达绕过 iframe 沙箱），排在最前；P1-4 的静态校验能拿到「看起来能跑」的大部分收益而风险远低于服务端执行；文件清单与单文件下载改动小、体验收益明确，随后再做。
