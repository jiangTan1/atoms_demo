# Design

## Context

参见 proposal.md 的 Why。本设计基于对本项目现状与 ADK 2.10.0 的核实：

- Agent 的 instruction 是模块级静态值（`app/agent/root_agent.py` 用 `build_instruction()` 拼装），进程内不会随请求变化，因此**每轮变化的上下文不能放在 instruction 里**。
- 现有做法是把每轮变化的信息拼进用户消息：`app/services/chat.py` 的 `compose_user_message()` 会前置 `[目标语言：X]`，再由 `app/api/chat.py` 传给 `stream_frames()`。这是本项目既有的「按轮注入」通道。
- 助手事件的 `parts` 中同时含 `thought=True` 的推理片段与正式回答，`extract_text()` 已按 `thought` 过滤。
- `app/services/chat.py` 的 `FrameBuilder.consume()` 已把 ADK Event 归一化为 SSE 帧：`partial=True` 增量下发并累积到 `_buffer`，`partial=False` 用累积文本补一个完整帧。
- `app/services/chat.py` 的 `events_to_messages()` 用 `_LANGUAGE_PREFIX_RE` 剥掉历史消息里的 `[目标语言：X]` 前缀。
- 会话事件已落盘（sqlite），`app/services/runner.py` 的 `get_session()` 可取回含 `events` 的会话对象。
- ADK 的 `BaseSessionService.append_event(session, event)` 是可用的公开方法，会把事件提交进会话并持久化；`Event` 可用 `author` + `content` 构造。

## Goals / Non-Goals

**Goals:**

- 三类意图边界行为可预期：领域外有固定回复、法规风险一律拒答、澄清追问有硬上限。
- 追问计数可靠，不依赖模型自己数轮次。
- 澄清控制标记对使用者完全不可见，包括流式过程中的瞬间闪现。
- 代码块可直接存为文件，会话标识可见。
- 不改变既有 SSE 帧协议与接口契约。

**Non-Goals:**

- 不做内容审核服务或敏感词库；法规风险由模型判断。
- 不做追问轮次的界面统计或可视化。
- 不做代码块文件名编辑、保存目录选择或批量导出。
- 不做多用户隔离与权限控制。

## Decisions

### 1. 三条意图规则全部落在提示词层，不引入分类器

在 `prompts/system.md` 新增「意图识别与边界」章节，按「领域外 → 法规风险 → 澄清追问」的顺序给出判据与固定话术。

- **理由**：本项目自始把意图识别交给模型（无分类器、无状态机），新增规则沿用同一取向，改动集中在提示词，可读可调。
- **备选**：引入规则引擎或关键词黑名单（被排除：法规风险是语义判断，关键词既漏又误，且与「不做审核服务」的非目标冲突）。

### 2. 领域外与法规风险的回复不计入澄清轮次

两类回复都必须**不带**澄清标记（见决策 3），因此计数自然归零（见决策 4），语义上正确：这两类回复是终态回答，不是追问。

### 3. 澄清请求用控制标记 `[[CLARIFY]]` 标识，服务端剥离

提示词要求：仅在需要澄清追问时，回复的第一行单独输出 `[[CLARIFY]]`；其余任何情况不得输出该标记。服务端在 `FrameBuilder` 中识别并剥离，标记不出现在下发的任何一帧中。

流式剥离必须处理「标记被切片」的情况：`[[CLARIFY]]` 固定 11 个字符，若直接按片下发，前几片会先出现半截标记。做法是在 `FrameBuilder` 中加一个开头判定缓冲：

- 回复开头尚未判定时先缓存，不下发；
- 缓存内容一旦成为标记前缀的延续（`marker.startswith(pending)`）就继续等；
- 一旦确认与标记不符，立即把缓存整体放出，之后走正常直通路径；
- 若确认以标记开头，丢弃标记本身，其余内容照常下发；
- 最终事件（`partial=False`）到达时无论判定是否完成都强制放出，避免卡住。

- **理由**：标记是让「追问」这一语义在服务端可判定、可计数的最简手段，且与既有「用可见文本承载结构」的做法（代码块语言标识）一致。
- **备选**：给 Agent 挂一个 `request_clarification` 工具，用工具调用计数（被排除：需要模型可靠触发 function call，免费模型稳定性不足，且工具返回值会再进入模型上下文，链路更长）；通过界面加「追问模式」开关（被排除：与既有「不增加界面控件」的取向冲突）。

### 4. 澄清轮次由服务端从会话事件推导，不写 session.state

计数函数放在 `app/services/chat.py`，入参是已取回的会话对象：

- 从最新事件向前遍历，**连续**出现的「带澄清标记的助手事件」计为轮次，遇到第一个不带标记的助手事件立即停止计数（该事件即非追问回复，链断开）。
- 用户事件不参与计数，仅用于分隔。
- 无事件的新会话轮次为 0。

- **理由**：与既有「ADK 是唯一事实来源、不另建表」的设计一致（见 `add-session-history-and-bug-finding` 决策 2）；不需要在写入路径上改造 ADK 的状态增量，读取顺序天然满足「同会话内连续追问」的语义。
- **备选**：把计数写入 `session.state`（被排除：ADK 的状态写入需经由事件的 `state_delta`，需要在 Runner 回调侧改造，收益不足）；建独立计数表（被排除：引入双写不一致）。

### 5. 轮次通过用户消息前缀注入

`compose_user_message()` 增加轮次参数，在既有语言前缀之后追加一行 `[澄清轮次：N/5]`（N 为已发生的追问轮次，N=0 时不注入）。提示词说明该标记的含义与上限规则。

- **理由**：沿用既有注入通道，不改动 Agent instruction 与 Runner 调用方式。
- **连带改动**：`events_to_messages()` 的前缀剥离正则需从「只剥语言前缀」扩展为「可重复剥离语言与轮次前缀」，否则历史会话回放会显示内部标记。

### 6. 达到上限由服务端短路返回固定结束语

当推导出的轮次 N ≥ 5 时，不再请求模型，直接产出「固定结束语」的 text 帧与 done 帧。

- 结束语为固定文案：无法准确理解意图，建议换一种说法或新建会话。
- 该轮的用户消息与结束语通过 `session_service.append_event()` 补写进会话，保证刷新页面后历史与刚才所见一致。
- **理由**：这是唯一能**保证**「5 次后一定结束」的实现方式；依赖模型遵循指令则无法保证。
- **备选**：仍然请求模型并注入「已到上限，必须输出结束语」（被排除：结果不确定）；短路但不落盘（被排除：刷新后本轮消息消失，看起来像缺陷）。
- **风险与退路**：若 `append_event` 在本项目用法下不可用（如构造的 `Event` 被 sqlite 实现拒绝），退化为短路但不补写，并在 README 与 Open Questions 中记录该行为。

### 7. 「另存为」按语言自动命名

在 `enhanceCodeBlocks()` 的 `code-head` 中，于「复制」旁新增「另存为」按钮，按检测到的语言映射扩展名后下载：

| 语言 | 扩展名 |
|---|---|
| java | `.java` |
| python | `.py` |
| csharp | `.cs` |
| cpp | `.cpp` |
| html | `.html` |
| javascript | `.js` |
| 未标注/其他 | `.txt` |

- 默认文件名为 `snippet.<ext>`；同一次渲染中出现同名时追加序号（`snippet-2.<ext>`），避免下载重名。
- 下载用 `Blob` + 临时 `<a download>`，不引入第三方库。

- **理由**：零打扰，一次点击即完成；扩展名映射与既有 `LANG_LABELS` 同源，无需新配置。
- **备选**：点击后弹输入框让使用者填名（被排除：多一步交互，且与「自动命名」的选择不符）。

### 8. 会话标识展示在顶栏状态区

新增一个只读元素显示当前会话 ID，字体等宽、可选中复制；无会话时显示占位文案（如「新会话（尚未创建）」）。

- 更新时机：收到 `done` 帧拿到 `session_id` 后、切换到历史会话后、载入本地会话成功后、新建会话后。
- **理由**：反馈的是排障信息，放在顶栏比消息区更稳定，不随消息滚动消失。

## Risks / Trade-offs

- [模型未按协议输出 `[[CLARIFY]]` 标记] → 计数无法推进、上限不触发。缓解：提示词用强约束描述并给出正反例；真机验收专门验证「连续追问是否被正确计数」。
- [模型在正常回复里误输出标记] → 该回复会被误判为追问，轮次虚高。缓解：提示词明确「除澄清追问外任何情况都不得输出」；验收时检查普通回答中不出现标记。
- [开头判定缓冲若处理不当会吞掉正文首字符] → 缓冲逻辑需在「确认不符」时整体放出，并补测试用例覆盖「首字符为 `[` 的普通回复」。
- [`append_event` 补写失败] → 退化为该轮不入库，历史中少最后一轮；在 README 的已知限制中说明。
- [法规风险的边界判断可能过宽，误伤正常安全类编程问题（如 SQL 注入防护、密码哈希）] → 提示词明确区分「防御性实现」与「探测/利用」，验收时验证前者正常作答。
- [另存为的文件名对所有代码块都是 `snippet` 前缀] → 属预期，避免读取代码内容猜测类名带来的不确定性。

## Migration Plan

1. 更新 `prompts/system.md`：意图识别与边界章节、表格输出偏好、澄清标记协议与上限规则。
2. 服务层：`compose_user_message` 增加轮次注入、新增轮次推导函数、`FrameBuilder` 增加标记剥离、`events_to_messages` 扩展前缀剥离。
3. 接口层：`app/api/chat.py` 计算轮次并在达到上限时短路返回。
4. 前端：另存为按钮与会话标识展示。
5. 补单元测试并跑通；再真机验收：领域外提问、法规风险提问、连续追问到上限、另存为下载、会话 ID 显示。

回滚：提示词与前端改动可独立回退；服务端的轮次注入与短路可通过恢复 `compose_user_message` 的签名与 `api/chat.py` 分支回退，不影响既有对话链路。

## Open Questions

- 达到上限时的固定结束语措辞是否需要使用者最终确认（本版先按设计给出，验收时可调整文案）。
- 是否为「已结束」的会话在界面上做视觉标记（本版不做，仅回复结束语）。
- `append_event` 补写这一轮是否会引起后续轮次的时间戳或排序异常，留待实现时真机确认。
