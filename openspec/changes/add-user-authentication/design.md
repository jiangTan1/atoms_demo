# Design

## Context

动机见 proposal.md 的 Why。本设计基于对项目现状与 ADK 2.10.0 源码的核实：

- `user_id` 目前是**客户端自报**的请求字段：`app/schemas.py` 的 `DEFAULT_USER_ID = "web-user"` 作为 `ChatRequest.user_id`、`SessionCreateRequest.user_id` 与各接口查询参数的默认值（`app/api/sessions.py`、`app/api/chat.py`、`app/api/workspace.py`），服务端无条件信任，没有任何校验。
- 会话落盘由 ADK 的 `SqliteSessionService` 管理（`app/services/runner.py` 的 `SQLITE_DB_PATH = PROJECT_ROOT / "data" / "sessions.db"`），该库的 schema 与迁移由 ADK 自己持有；`SESSION_BACKEND` 可在 `sqlite` 与 `memory` 间切换。
- 会话按 `app_name + user_id` 归属（`app/services/runner.py` 的 `create_session/get_session/list_sessions`），因此「会话归属谁」完全由传入的 `user_id` 决定，改成登录用户名即可完成隔离，无需改 ADK 层。
- 文件沙箱目录为 `data/workspace/<session_id>/`（`app/services/workspace.py`），**按会话而非按用户**隔离；只要下载前校验会话归属，即可保证用户之间不串沙箱。
- 前端为单页 `web/index.html` + `web/app.js`（616 行，含 4 处 `fetch`：对话、会话列表、历史消息、打包下载），无构建步骤，脚本直接以 `<script src="/app.js">` 引入。
- 配置层（`app/config.py`）已固定「环境变量 + 启动期校验」的取向：必填项缺失即抛 `ConfigError` 并点名配置项，可选项走 `_positive_int()` 之类的带默认值读取。
- `app/main.py` 的 `create_app()` 依次挂三个 `/api/*` 路由，最后把 `web/` 以 `StaticFiles(html=True)` 挂在 `/`。

## Goals / Non-Goals

**Goals:**

- 访问服务的第一步是认证：未登录不得进入对话界面，也不得触发任何业务动作。
- 会话与文件沙箱有可证明的归属：由登录态决定，客户端无法指定或伪造。
- 密码只以加盐哈希保存，校验走哈希比对。
- 账号容量有上界（普通用户 99），默认管理员开箱可用。
- 认证失败、登录态过期、权限不足都给出中文提示，不白屏、不静默。

**Non-Goals:**

- 不做 HTTPS 终止、口令复杂度策略、登录失败锁定、验证码、找回密码（含邮件/短信）。
- 不做「记住我」、多设备管理、登录态续期与刷新令牌。
- 不做管理员的可视化管理界面：管理员的新增 / 重置 / 删除以接口形式提供，界面不在本变更范围（见 Open Questions）。
- 不做既有匿名会话的迁移与认领，只保证它们不再对任何用户可见。
- 不做细粒度资源 ACL（本变更只区分「管理员」与「普通用户」两种角色）。

## Decisions

### 1. 账号与登录态落在独立的 `data/users.db`，用标准库 `sqlite3`

- **理由**：`data/sessions.db` 的 schema 由 ADK 的 `SqliteSessionService` 持有，往同一个库里塞业务表会与 ADK 的内部结构与后续迁移耦合；且 `SESSION_BACKEND=memory` 时会话不落盘，而**账号数据必须始终持久化**（否则重启即丢账号、默认管理员被反复重建）。独立库让账号的持久化与 `SESSION_BACKEND` 解耦，`data/` 已被 `.gitignore` 覆盖，无需改忽略规则。
- **与 proposal 的差异**：proposal 的 Impact 写的是「`data/sessions.db` 新增用户表与登录态表」，本设计改为独立 `data/users.db`，原因是上述的持久化与解耦。数据面范围不变（仍在 `data/` 下、仍不进版本控制）。
- **备选**：写进 `data/sessions.db`（被排除：与 ADK 的 schema 同库，且 memory 后端下账号随之丢失）；引入 ORM 或第三方库（被排除：为标准库足够的关系足够简单引入依赖不划算）。

### 2. 登录态用服务端随机会话令牌 + HttpOnly Cookie

- **做法**：登录成功时用 `secrets.token_urlsafe(32)` 生成令牌，写入登录态表（令牌、用户名、创建时间、过期时间），把令牌放进 Cookie（`HttpOnly`、`SameSite=Lax`、`Path=/`、`max_age` 为 1 天）。请求时从 Cookie 取令牌查表，取不到、已过期或用户已删除即视为未登录。退出登录与改密时删除对应记录。
- **理由**：改密后失效其他登录态（spec 要求）在服务端表上只是「按用户名删掉令牌记录」，用签名 Cookie（如 itsdangerous）反而要额外维护吊销名单，成本更高；HttpOnly 让令牌不被页面脚本读取，降低 XSS 窃取面。
- **备选**：签名 Cookie / JWT 无状态令牌（被排除：改密吊销需要额外黑名单，且需新增依赖或手写签名）；把令牌放 `localStorage` 由前端在请求头携带（被排除：脚本可读，XSS 面更大，且失去 Cookie 的自动携带便利）。

### 3. 鉴权用 FastAPI 依赖注入，不用全局中间件

- **做法**：提供一个鉴权依赖（从 Cookie 解析登录态 → 返回当前用户），`chat` / `sessions` / `workspace` 各路由声明该依赖；`/api/auth` 下的注册、登录、当前身份查询接口不声明（前两者本就无需登录，当前身份查询在依赖内自行判定并返回 401）。
- **理由**：白名单是「少数接口不需要登录」，依赖注入让每个接口的鉴权要求在签名里可见，比在中间件里维护一份路径白名单更不容易漏；同时失败时能直接在依赖里抛带中文 detail 的 401。
- **备选**：全局中间件按路径前缀放行（被排除：路径白名单与路由定义分离，新增接口时容易漏配）；逐个接口手写 Cookie 解析（被排除：重复代码多、容易不一致）。

### 4. 会话归属用 `user:<登录用户名>` 作为 ADK 的 `user_id`

- **做法**：`app/services/runner.py` 的调用侧统一把登录用户名转成 `user:<username>`，作为 `user_id` 传给 ADK。
- **理由**：既有的匿名会话以 `user_id = "web-user"` 落盘，而 `web-user` 本身是一个合法的 8 字符用户名；若直接用用户名，**任何注册到该名字的人会看到历史匿名会话**。加固定前缀后，登录用户的 `user_id` 永远不可能等于 `web-user`，spec 要求「既有匿名会话不再展示」自然成立，且不需要改库、不需要迁移。
- **备选**：直接用用户名（被排除：如上，存在与既有匿名标识碰撞的窗口）；启动时清理或迁移匿名会话（被排除：破坏性操作，且 proposal 明确不迁移）。

### 5. 密码哈希用标准库 `hashlib.pbkdf2_hmac` + 每账号随机盐

- **做法**：盐为 `secrets.token_bytes(16)`，哈希为 `hashlib.pbkdf2_hmac("sha256", password, salt, iterations)`，存储为单字段字符串 `pbkdf2_sha256$<iterations>$<salt_b64>$<hash_b64>`；校验时按存储的迭代数与盐重算，用 `hmac.compare_digest()` 做定时安全比较。
- **理由**：不新增第三方依赖（proposal 已明确），标准化字符串自带参数便于日后调高迭代数而不破坏既有数据；定时安全比较避免按字节提前返回带来的时序侧信道。
- **备选**：引入 `bcrypt` / `passlib`（被排除：新增依赖，与项目「引入依赖需谨慎」的取向不符）；`hashlib.scrypt`（被排除：参数调优更复杂，收益在当前演示场景下不明显）。

### 6. 账号表加 `source` 列，把「99 上限」的口径落到数据上

- **做法**：账号表包含 `username`（主键）、`password_hash`、`role`（`admin` / `user`）、`source`（`system` / `self` / `admin`）、`created_at`。自助注册上限的判定为 **`role='user' AND source='self'` 的行数 < 99**；默认管理员为 `source='system'`，管理员新增的账号为 `source='admin'`。
- **理由**：spec 同时要求「普通用户总数不超过 99」与「管理员新增用户不占用自助注册的 99 个名额」、以及「管理员（root）不占名额」。三者只有在区分**来源**时才能同时成立；`source` 只多一列，是满足既有 spec 的最小代价。
- **备选**：只用 `role` 计数（被排除：管理员新增的普通用户会占用名额，与 spec 冲突）；不区分来源、把上限理解成「全部账号 ≤ 99」（被排除：会让默认管理员与管理员新增的账号都挤占名额，偏离「最多允许 99 个用户注册」的原意）。

### 7. 默认管理员在应用启动的 lifespan 中初始化

- **做法**：在 `app/main.py` 的 `lifespan` 里创建账号服务并执行「账号表为空时插入 `root`/`root`（`role='admin'`, `source='system'`）」。表已非空则不做任何写入。
- **理由**：复用既有的启动装配点，账号初始化与 Runner 装配在同一处完成，失败即在启动阶段暴露；判定条件用「表为空」而非「root 不存在」，因此**管理员把 root 改名/删除的意图不会被启动逻辑回滚**——不过 spec 已禁止删除 root，且用户名不可改，因此「表为空」等价于「首次启动」。
- **备选**：惰性初始化（首次登录时创建）（被排除：失败点被推迟到使用者操作时，诊断更差）；用 CLI 命令初始化（被排除：多一套运维步骤，与「开箱可用」冲突）。

### 8. 归属变更落在接口层，不动 ADK 层

- **做法**：`app/schemas.py` 移除 `ChatRequest.user_id` 与 `SessionCreateRequest.user_id`；三个接口把 `user_id` 参数从「查询参数/请求体字段」改为「取自鉴权依赖」；`app/api/workspace.py` 的下载接口在查会话时传入登录用户的 `user_id`，查不到即按「会话不存在」返回 404。
- **理由**：会话与沙箱的归属判定已经由 `get_session(..., user_id=...)` 完成，只要把 `user_id` 的来源换成登录态，隔离即成立，无需在 ADK 层或沙箱层新增判断；「他人会话按不存在处理」也自然满足（查不到就是 `None`）。
- **连带结论**：`file-workspace` 的 delta 只需要「下载前归属校验」这一条，沙箱目录结构不变，既有沙箱安全与配额逻辑完全复用。
- **备选**：在沙箱层按用户再分一层目录（被排除：会话 ID 已全局唯一，再分层不增加安全性，反而改动面更大）。

### 9. 前端认证界面并入既有 `index.html` / `app.js`，不新开文件

- **做法**：`index.html` 新增认证区块（注册 / 修改密码 / 登录三个入口按钮 + 用户名密码输入框 + 登录与取消按钮 + 提示区），未登录时显示该区块、隐藏对话区；`app.js` 在启动时先请求「当前身份」，成功才执行既有的 `bootstrap()`，并集中处理 401（任何接口返回 401 即切回认证界面并提示重新登录）。认证区块里「注册」是切换表单的入口，「修改密码」按决策 11 只作入口提示。
- **理由**：现状是无构建的单页 + 单脚本，认证仅增加约一个区块与一组函数；并入 `app.js` 可避免新脚本与 `app.js` 之间的初始化顺序耦合（认证成功后要接着跑 `bootstrap()`）。CDN 未加载时的纯文本降级逻辑继续生效（认证界面不依赖任何 CDN 库）。
- **备选**：新增 `web/auth.js`（被排除：需要定义两文件间的初始化契约，收益只是文件更短）；把认证做成独立页面（被排除：多一次跳转，且登录态展示与顶栏要跨页同步）。

### 10. 新增一个可选配置项 `AUTH_COOKIE_SECURE`

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `AUTH_COOKIE_SECURE` | `false` | 为 `true` 时登录态 Cookie 带 `Secure`，仅在 HTTPS 下浏览器会回传 |

- **理由**：无 HTTPS 时 Cookie 明文传输（proposal 已列为部署风险）；是否加 `Secure` 取决于部署是否已终止 TLS，属运维策略，符合项目「环境变量配置」的取向。默认 `false` 保证本机演示与内网 HTTP 可用，部署到 HTTPS 后置为 `true`。
- **备选**：按 `request.url.scheme` 自动判定（被排除：经 Nginx 反代后应用内看到的仍是 `http`，判定不可靠）；恒开 `Secure`（被排除：HTTP 演示环境下浏览器不回传 Cookie，直接不可用）。

### 11. 改密只对已登录用户开放，入口放在对话界面顶栏

- **做法**：`POST /api/auth/password` 保持「要求已登录」不变（见决策 3、access-control spec）。前端把改密做成对话界面顶栏上的一个入口（与「退出登录」同排），点击后弹出改密表单（原密码 + 新密码，用户名取当前登录用户、不需要重填），提交直接调 `/api/auth/password`；成功后关闭表单并保持登录（服务端 `revoke_other_tokens(keep_token=...)` 只吊销其他登录态）。认证界面上的「修改密码」按钮只作入口提示：点击后提示「修改密码需要先登录」，不进入任何可提交的改密表单。
- **理由**：改密在语义上要求「证明你是这个账号」——原密码就是该证明，而它同时也是一次登录凭据；但把「未登录也能改密」实现在前端，就必须先偷偷登录再改密再退出，会留下短暂的额外登录态，且失败路径（新密码不合规、网络中断）会把使用者留在一个说不清的中间状态。因此把改密收进已登录界面：一次请求、无中间态，且与 `access-control` spec「除注册 / 登录 / 当前身份外都要登录态」的约束完全一致。认证界面保留「修改密码」按钮是为了满足 web-chat spec 对三个入口按钮的要求，同时给出明确的下一步指引。
- **备选**：认证界面填「用户名 + 原密码 + 新密码」并由前端串联「登录 → 改密 → 退出」（先前实现，被排除：多两次请求、有中间登录态、失败路径状态不清）；后端新增一个免登录的「凭原密码改密」接口（被排除：等于新增一个无登录态的凭据校验入口，扩大了攻击面，且与 access-control spec 冲突）。

## Risks / Trade-offs

- [BREAKING：既有匿名会话与沙箱对所有人不可见] → 属有意行为（proposal 已声明不迁移）；README 注明「升级后旧会话不再展示」，数据仍保留在 `data/` 中可人工取回。
- [既有单元测试几乎全部直连接口、不带登录态，改造后会集体失败] → 在测试夹具中新增「注册并登录、取得 Cookie」的辅助函数，统一注入；把「未登录返回 401」写成显式用例，让破坏性变更被测试固化。
- [无 HTTPS 时 Cookie 与口令明文传输] → 部署章节要求以 Nginx 终止 TLS，并在 HTTPS 就绪后把 `AUTH_COOKIE_SECURE` 置为 `true`；HTTP 仅限本机与内网演示。
- [默认口令 `root`/`root` 与 3 字符的密码下限属演示级取舍] → 写入 README 已知限制，明确「上线前必须修改默认口令」，并在文档中说明下限偏松是有意为之（便于演示）。
- [sqlite 与多 worker 并发写] → 沿用既有约束：生产以 `--workers 1` 运行；账号侧的「先查计数再插入」放在同一事务内执行，降低超限竞态。
- [管理员操作只有接口、没有界面，使用门槛较高] → 在 README 给出可直接复制的调用示例（含 Cookie 获取方式）；是否补界面记入 Open Questions，待明确需求后再做。
- [用户名区分大小写，可能出现 `Alice` 与 `alice` 并存造成混淆] → 本版按原样保存与比较（不额外规范化），记入 Open Questions；若需防混淆可在后续加 `COLLATE NOCASE` 唯一约束。
- [登录态表随登录次数增长] → 每次登录前清理该用户的过期记录，并在鉴权查询时把过期记录视为无效；数据量在有界用户数下可忽略。

## Migration Plan

1. 配置层：新增可选配置项 `AUTH_COOKIE_SECURE`（默认 `false`）。
2. 新增 `app/services/accounts.py`：`data/users.db` 的建表、密码哈希与校验、账号 CRUD、登录态令牌的签发/校验/吊销、默认管理员初始化。
3. 新增 `app/api/auth.py`：注册、登录、退出登录、修改自己的密码、当前身份查询，以及管理员的用户管理接口；连同鉴权依赖（从 Cookie 解析登录态）。
4. `app/schemas.py`：移除 `ChatRequest.user_id` 与 `SessionCreateRequest.user_id`，新增认证相关请求/响应模型。
5. `app/api/chat.py`、`app/api/sessions.py`、`app/api/workspace.py`：声明鉴权依赖；`user_id` 一律取自登录态并加 `user:` 前缀。
6. `app/main.py`：lifespan 初始化账号服务与默认管理员；挂载 `auth` 路由（在静态前端之前）。
7. 前端：`index.html` 加认证区块；`app.js` 加登录态门控、认证交互与 401 集中处理。
8. 更新测试夹具并补认证单测；再真机验收：未登录拦截、注册/登录/改密/退出、99 上限、改密使其他登录态失效、跨用户会话与下载隔离、管理员新增/重置/删除。

回滚：认证改动集中在新增的账号服务、认证路由与三个接口的依赖声明上。回退时删除 `auth` 路由与依赖声明、恢复 `schema` 中的 `user_id` 字段即可回到「无鉴权」形态；`data/users.db` 为独立文件，删除它不影响既有会话数据。

## Open Questions

- 管理员是否需要一套可视化管理界面（本版只提供接口）——待明确使用场景后再评估。
- 用户名是否应改为大小写不敏感（防 `Alice` / `alice` 混淆）——本版按原样比较。
- 是否允许管理员把普通用户提升为管理员，或新增管理员——本版只按 spec 提供新增普通用户、重置密码与删除。
- 登录态有效期（1 天）与 `AUTH_COOKIE_SECURE` 是否需要一并做成可配置项——本版 TTL 固定 1 天，仅 `Secure` 可配。
